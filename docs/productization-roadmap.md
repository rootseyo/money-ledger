# 10억 가계부 제품화 로드맵

작성일: 2026-10-09  
목표: 현재 운영 중인 기능을 개인 사용자와 가족 단위의 제한 베타에 안전하게 제공하고, 운영·지원이 가능한 정식 서비스로 전환한다.

## 현재 상태와 판단

회원가입, 이메일 로그인, 카카오 OAuth, 체험용 데모, 약관 동의, 목표 금액을 설정하는 가계부 생성·초대 흐름, 거래·고정비·자산·통계 화면은 구현되어 있다. 기존 사용자 데이터도 가계부를 만드는 과정에서 연결하는 경로가 있다. 따라서 제품화의 중심은 핵심 화면 추가보다 운영 조건과 데이터 보호를 완성하는 일이다.

확인한 출시 위험은 다음과 같다.

- 개인정보 처리방침에 운영자와 문의처가 환경변수 미설정 시 “준비 중”으로 노출된다. 데이터 보유·삭제와 회원 요청 처리는 운영자 문의 방식으로만 설명되어 있다.
- 가계부, 초대 코드, 회원 연결 정보가 `SystemSetting`의 JSON/문자열 키로 관리되고, 사용자당 가계부 연결도 단일 값이다. 만료·회수 가능한 초대 관리와 역할 기반 권한 모델을 확인하기 어렵다.
- 로그인 제한은 프로세스 메모리 Map에 저장되어 다중 인스턴스에서 공유되지 않는다. 클라이언트 IP는 요청의 `x-forwarded-for` 첫 값을 사용한다.
- 배포는 원격에서 `npm install` 후 빌드·PM2 reload를 수행한다. 자동 백업·복구 확인·배포 후 smoke test·롤백 절차는 스크립트에 없다.
- 인증 DB 통합 테스트는 `AUTH_TEST_DATABASE_URL`이 없으면 건너뛴다. 실제 CI/운영 빌드에서 이 테스트가 항상 실행되는지는 별도 확인이 필요하다.
- 최근 운영 배포 로그에는 npm audit high 취약점 5건이 표시된 적이 있다. 현 시점의 재검증과 조치 여부 확인이 필요하다.
- 익명 커뮤니티는 현재 안내 문구 수준이며 제품 기능은 아니다. 금융 정보의 공개 범위와 운영 정책을 정하기 전까지 출시 범위에서 제외한다.

이 계획은 제품·운영 우선순위 제안이며, 개인정보 처리방침과 약관은 실제 운영 방식에 맞춰 개인정보 전문 검토를 거쳐 게시한다. 개인정보 보호법은 안전조치 의무를 규정하고 처리방침 수립·공개를 요구하므로, 문서의 문구뿐 아니라 실제 시스템 설정과 일치시켜야 한다. [개인정보 보호법 제29조](https://www.law.go.kr/LSW/lsLawLinkInfo.do?chrClsCd=010202&lsJoLnkSeq=900079357), [개인정보 보호법 제30조](https://law.go.kr/LSW/LsiJoLinkP.do?languageType=KO&lsNm=%EA%B0%9C%EC%9D%B8%EC%A0%95%EB%B3%B4+%EB%B3%B4%ED%98%B8%EB%B2%95&paras=1)

## P0 진행 현황 (2026-10-10)

- **구현됨, 운영 검증 필요:** 회원 데이터 JSON 내보내기와 탈퇴 API/UI, 가계부에서 나가기·소유권 이전·구성원 내보내기·가계부 삭제, 초대 코드 30일 만료·재발급, PostgreSQL 원자적 rate limit, 신뢰 프록시 IP 처리, DB health endpoint를 추가했다. 가계부·초대는 기존 `SystemSetting` JSON 모델을 유지하므로 관계형 모델 전환은 별도 과제다.
- **배포 안전장치 구현, 불완전:** 사전 환경변수 검사, `.env` 권한 600, `npm ci`, 배포 후 health check와 격리 PostgreSQL CI workflow를 추가했다. 현재 원격 배포 스크립트는 실패 시 자동 롤백하지 않고, 별도 보관소 백업/복구 연습도 구성되지 않았다.
- **운영자 설정 미완료:** 개인정보 문의 이메일(`PRIVACY_CONTACT_EMAIL`)은 로컬 `.env`에 있고 권한은 600이다. 운영자 표시명이 비어 있어 운영 환경 사전 검사는 현재 실패한다. 배포 전 운영자 표시명을 확정하고 프로덕션 환경에 등록해야 한다.
- **미완료:** 오프사이트 암호화 백업과 실제 복구 연습, 자동 롤백, CI에서 실제 PostgreSQL 통합 테스트가 통과한 결과, 가구/초대 관계형 모델 전환, 운영자 표시명 확정이 남아 있다.
- **검증 상태:** `npm test` 81개 통과, DB 통합 테스트 1개는 격리 PostgreSQL 부재로 로컬에서 건너뜀. `npm run build`, 변경 파일 ESLint, `bash -n deploy.sh`, `git diff --check` 통과. `npm audit --omit=dev` 취약점 0건. 전체 `npm audit`의 개발 도구 체인 high 항목은 upstream 패치 여부를 확인해 안전하게 처리해야 하며 Next.js를 하위 메이저로 강제 낮추지 않는다. 전체 ESLint는 기존 오류가 있어 CI 게이트로 추가하지 않았다.

**P0 통과 기준:** 위 9개 완료, 데이터 복구 연습 성공, 출시 대상 기기에서 이메일/카카오 가입·로그인과 초대 수락 확인, 교차 가계부 접근 테스트 통과, 처리방침 문의 경로 실동작. 그 전까지는 공개 광고보다 운영자가 관리하는 제한 베타가 적절하다.

## P1 — 제한 베타에서 확인하고 정식 출시 전에 마무리

1. **온보딩과 복구 경험**: 이메일 비밀번호 재설정, 계정 중복/탈퇴 후 재가입 안내, 카카오 연동 해제 시 데이터 처리, 가계부를 만들지 않고 나간 사용자의 재진입, 데모에서 실제 계정으로 전환 안내를 점검한다.
2. **데이터 품질**: 거래 중복 방지와 수정 이력, 가져오기 미리보기/오류 복구, 삭제 확인·되돌리기 정책, 통계 경계값(월말·시간대·환불·이체)을 실제 데이터 표본으로 검증한다.
3. **관측과 지원**: 서버 오류율, DB 연결/용량, 예약 작업 성공, 백업 성공, Kakao 콜백 실패를 확인하는 대시보드와 알림을 둔다. 개인정보를 과다하게 로그에 남기지 않는 기준과 장애 대응 문서를 만든다.
4. **사용성·접근성**: 모바일 화면, 키보드 탐색, 입력 오류 안내, 차트 대체 설명, 색상 대비, 빈 화면과 느린 네트워크 상태를 점검한다. 5~10가구 사용성 인터뷰에서 초대·첫 거래 등록 완료율과 혼란 지점을 기록한다.
5. **상품 경계**: 데모 데이터 초기화/보유 정책과 가족 구성원별 데이터 가시성을 사용자에게 분명히 보여준다. 금융 자문이나 은행 자동연동으로 오해할 수 있는 표현을 점검한다.

**P1 통과 기준:** 초대받은 신규 사용자 80% 이상이 도움 없이 첫 거래를 등록하고, 핵심 흐름에서 P0/P1 결함이 없으며, 2주 파일럿 동안 백업·알림·예약 작업이 정상 동작한다. 표본 수가 작으므로 수치는 방향성 기준으로 사용하고 실제 관찰 결과와 함께 판단한다.

## P2 — 사용성 검증 후 확장

- 공개 랜딩 페이지와 검색 콘텐츠를 로그인 설명 화면과 분리하고, 기능·데이터 처리·가격/무료 범위를 명확히 안내한다.
- 익명 금융 커뮤니티는 게시물 신고, 차단, 운영자 검토, 개인정보/계좌정보 노출 방지, 삭제·보존 기준을 먼저 설계한 뒤 별도 베타로 출시한다.
- 여러 가계부 전환, 가구별 권한 설정, 초대 링크, 관리자 활동 기록을 실제 수요에 맞춰 확장한다.
- 가입 완료, 첫 가계부 생성/조인, 첫 거래 입력, 7일 재방문, 오류/지원 요청을 개인정보 최소 수집 원칙에 맞춰 측정한다.
- 가입자가 늘어 부하·복구 목표를 넘기기 시작할 때 DB 확장, 캐시, 다중 인스턴스, 장애 복구 구성을 단계적으로 검토한다.

## 실행 순서와 대략 일정

| 기간 | 결과 |
|---|---|
| 1주차 | 운영 정보·지원 경로 확정, 처리방침 데이터 흐름 대조, 취약점 및 배포/백업 현황 점검 |
| 2–3주차 | 가계부 스키마·권한·초대 개선, 회원 데이터 요청/탈퇴 흐름, 공유 데이터 격리 테스트 |
| 4주차 | 운영형 rate limit, 백업 복구 연습, CI 인증 통합 테스트, 배포 health check/rollback 정비 |
| 5–6주차 | 5–10가구 제한 베타, 사용성·오류·지원 지표 수집, P0/P1 결함 처리 후 정식 출시 판정 |

일정은 한 명의 개발자가 병행 작업하는 기준의 초안이며, 개인정보 검토와 데이터 모델 변경 범위에 따라 조정한다. 공개 출시 날짜는 P0 검증 결과를 확인한 뒤 확정한다.
