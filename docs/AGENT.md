# 가계부 독립 서비스 구현 가이드

## 목표와 범위

가계부를 기존 관리자 사이트에서 분리해 독립 도메인(예: `https://money.example.com`)에서 독립적으로 운영한다. DNS 레코드가 올바른 서버를 가리키는지, 프록시·터널·HTTPS가 구성되어 있는지는 구현·배포 단계에서 대시보드와 서버 설정으로 확인한다. 이 문서 작성만으로 DNS, 서버, 코드 또는 운영 DB를 변경하지 않는다.

독립 서비스의 최소 범위는 거래 장부, 월간 요약·분석, 달력, 월별 고정비, 거래 입력·CSV/대량 가져오기, 카테고리·결제수단, 예산, 자산, 모바일 푸시 수신, Slack 리포트, 개인정보 가리기, 화면 잠금과 패스키다. 사용자가 여러 명인 공개형 SaaS나 결제·초대 기능은 별도 요구가 있기 전에는 포함하지 않는다. 첫 배포는 기존 운영자만 접근할 수 있는 비공개 서비스로 한다.

## 권장 구조

- 새 Git 저장소와 별도 Next.js 앱으로 추출한다. 화면과 API를 옮길 때 기존 관리자 셸, 앱 디렉터리 등록, 다른 관리 서비스의 DB 모델에 런타임 의존성이 남지 않게 한다.
- 독립 실행 디렉터리 예시는 `/home/deploy/services/money-ledger`, 프로세스 이름은 `money-ledger`, 포트는 `4010`이다. 실제 포트는 서버 점유 상태를 확인한 뒤 확정한다.
- PostgreSQL 서버는 우선 재사용할 수 있지만, 서비스 전용 DB와 DB 사용자·권한을 만든다. 연결 문자열, JWT 서명키, 모바일 API 토큰, `CARD_API_KEY`, `CRON_SECRET`, Slack 설정은 기존 앱과 분리하고 새 `.env`에 비밀값을 커밋하지 않는다.
- 서비스 전용 Prisma schema와 migration을 둔다. 최소 모델은 관리자/사용자, `CardTransaction`, 설정, API 토큰 및 필요한 감사 기록이다. 새 저장소에 현재 모노레포의 전체 Prisma schema와 무관한 앱 모델·마이그레이션을 복사하지 않는다.
- 초기에 1인용으로 출시하더라도 거래·설정 쿼리는 소유자 경계를 명시한다. `SystemSetting`의 고정 키를 그대로 전역 공유하지 말고 owner ID를 키 또는 별도 관계에 포함해 다른 사용자의 고정비·예산·자산·카테고리가 섞이지 않게 한다.

## 기존 코드에서 이전할 기능

필요한 범위만 선택적으로 추출한다. 기존 모듈 위치를 출발점으로 삼되, 관리자 앱의 공통 레이아웃이나 인증 컨텍스트를 직접 import하지 않도록 새 서비스 안에서 의존성을 정리한다.

- 화면: `src/app/admin/card-history`의 장부, 달력, 통계, 고정비, 자산·카테고리 UI와 필요한 CSS·훅·유틸리티.
- API: `src/app/api/card-transactions`, 해당 앱에서 실제 사용하는 `src/app/api/financial-assets`, 주식 조회, 일간·월간 리포트 엔드포인트.
- 서비스 로직: `src/lib/card-service.ts`, 거래 분류·날짜·정렬·고정비 스케줄·CSV 파서 등 가계부 전용 라이브러리.
- 보안: 현 `/admin` 페이지 프록시는 페이지 경로만 검사한다. 독립 앱의 `src/proxy.ts`에서도 로그인 경로를 제외한 화면을 보호하되, 데이터 API는 각 Route Handler에서 세션 또는 검증된 토큰을 직접 확인한다.

기존 API의 푸시 수신 JSON 규격과 중복 판정은 모바일 앱과 대조해 호환성을 유지한다. 기존 푸시 연동의 기본 인증은 `CARD_API_KEY` 또는 발급 토큰 방식이다. 모바일 앱에서 서버 주소를 변경할 수 있는 설정이 있는지 확인하고, 없으면 새 도메인을 앱 설정에 반영한 뒤 구버전 앱이 어느 기간 동안 기존 주소를 써야 하는지 정한다. 거래 조회 `GET`을 포함한 모든 API에서 인증과 소유자 검사를 확인한다. 로그인되지 않은 브라우저에서 가계부 데이터가 응답하는 경로를 남기지 않는다.

## 로그인·쿠키·패스키

- 기존 `Admin` 테이블을 다른 관리자 앱과 계속 공유하지 않는다. 1인용 운영자 자격 증명은 새 DB에 안전하게 이전하되, 새 서비스의 활성 상태 확인·비밀번호 해시 검증·로그인 실패 제한·로그아웃을 구현한다. 첫 로그인 뒤 비밀번호 변경 절차를 제공한다.
- 세션 서명키는 새 서비스 전용으로 발급하고 기존 `JWT_SECRET`을 복사하지 않는다. 세션 쿠키는 `Secure`, `HttpOnly`, `SameSite`를 설정하고 도메인 속성을 생략해 호스트 전용 쿠키로 제한한다. `/admin/card-history` 경로에 한정된 필터 쿠키는 독립 루트 경로 `/`에 맞게 이전한다.
- CSRF 보호와 요청 출처 검사를 상태 변경 API에 적용한다. 모바일 API 토큰은 웹 세션과 분리하고, 가능한 범위에서 거래 쓰기 권한만 부여하며 회전·폐기할 수 있게 한다.
- 패스키 설정은 `WEBAUTHN_ORIGIN=https://money.example.com`, `WEBAUTHN_RP_ID=money.example.com`처럼 실제 공개 주소와 일치시킨다. Origin과 RP ID는 요청 Host를 무조건 신뢰해 만들지 말고 배포 설정의 허용값을 사용한다. 도메인이 바뀌면 패스키 재등록이 필요할 수 있으므로 비밀번호 로그인과 복구 경로를 먼저 확보한다.
- 개인정보 모드는 화면 표시만 가린다. 서버 인증·네트워크 응답·로그·접근권한을 대신하지 않는다. 화면 잠금은 보안 경계를 강화하는 UI일 뿐, 모든 API 응답을 잠그는 서버 측 세션 폐기 기능과 혼동하지 않는다.

## DB 데이터 이전

1. 원본 DB 백업을 만들고 복구 절차를 확인한다. 운영 데이터에 직접 임시 스크립트를 실행하지 말고, 마스킹 또는 별도 복제 DB에서 이전 과정을 먼저 검증한다.
2. 새 스키마와 migration을 준비한다. 기존 `CardTransaction` ID, 금액, `notifiedAt`, `createdAt`, 보고 상태, 원본 JSON을 가능한 한 보존한다.
3. 설정을 서비스 사용자에 연결해 이전한다. 대상에는 `household_fixed_expenses`, `household_payment_methods`, `household_categories`, `household_budget`, `financial_assets_data`, `admin-screen-passkeys:<adminId>`, `card-list-order:<adminId>:ledger`와 `household-fixed-month:YYYY-MM` 스냅샷이 포함된다. 로그인 인증서·토큰은 소유자를 확인하고 필요한 경우 회전한다.
4. 고정비 변경사항은 `docs/card-history-monthly-fixed-expenses.md`와 실제 운영 스키마·migration 상태를 비교한다. 미적용 migration을 운영 DB에 임의로 적용하지 않는다. `fixedExpenseId`, `fixedOccurrenceKey`, `scheduledFor` 필드가 사용된다면 중복 키와 기존 거래 연결을 확인한다.
5. 이전 전후 거래 건수와 월별 합계(수입·지출·저축·이체), 보고 상태, 고정비 설정 건수 및 금액을 비교한다. 고정비가 다시 생성되거나 수입·저축 분류가 바뀌지 않았는지 확인한다. 완료 전에는 이전 DB를 삭제하거나 쓰기 가능 상태에서 폐기하지 않는다.

## 프록시·HTTPS·프로세스

- 공개 HTTPS 요청은 프록시와 서버 사이까지 암호화한다. 서버에서 Nginx/Caddy 등으로 도메인을 새 앱 포트에 전달하고, SSL/TLS 모드는 유효한 원본 인증서를 사용하도록 설정한다. 다른 앱으로 전달되거나 기본 도메인의 쿠키가 공유되지 않는지 확인한다.
- 배포 스크립트는 기존 `deploy.sh`를 그대로 재사용하지 않는다. 현재 스크립트는 `/home/deploy/work/admin`에 `rsync --delete`를 실행하고 `admin-payment`를 재시작하므로 독립 앱 파일이나 프로세스에 사용하지 않는다. 새 저장소 전용 배포 스크립트와 DB 백업을 준비하고, 전용 경로·환경파일·포트·PM2 이름만 변경하도록 범위를 제한한다.
- 카드 푸시·일간/월간 Slack 작업의 주소도 새 도메인과 서비스 포트에 맞춘다. 기존 `scripts/run-card-report.mjs` 기본 주소는 `127.0.0.1:4000`이므로, 새 서비스에서는 환경변수로 URL을 설정하고 비밀키가 로그에 노출되지 않게 한다.

## 구현 순서와 완료 조건

1. **현황 고정:** 기존 API 호출, Android 푸시 발신 주소·인증 방식, 필요한 환경변수, DB 설정 키, 보고 자동 실행 방식을 목록화한다.
2. **독립 앱 골격:** 새 저장소, Next.js 앱, 로그인 화면, 호스트 전용 세션, 서비스 전용 Prisma schema/DB 연결을 만든다.
3. **핵심 경로:** 거래 수신·조회·수정, 월간 통계, 고정비, 카테고리와 설정을 소유자 검사와 함께 이전한다. 그 다음 달력, 자산, Slack, 패스키를 붙인다.
4. **데이터 이전 준비:** 복제 DB로 이전 스크립트를 작성하고 월별 대사 결과와 되돌리기 절차를 만든다.
5. **독립 배포:** 기존 앱에 영향을 주지 않는 새 PM2 프로세스와 포트로 배포하고, Cloudflare·원본 HTTPS를 연결한다. DB migration은 검토된 순서로 적용한다.
6. **점진 전환:** 로그인, 모바일 푸시, 거래 중복, 월 경계의 고정비 집계, Slack, 패스키, 백업·복원을 확인한 뒤 휴대폰 발신 주소를 전환한다. 이전 앱은 전환 확인 기간 동안 롤백 용도로 둔다.

완료 조건은 새 도메인에서 기존 관리자 앱의 로그인이나 DB 설정 없이 독립 로그인과 가계부 사용이 가능하고, 모바일 거래 수신·월별 합계·납부일 기준 고정비가 기존 데이터와 일치하며, 인증 없는 조회가 차단되고, 새 서비스만 단독 배포·복구할 수 있는 것이다. DNS 전환, 운영 DB migration, 앱 배포는 각각 별도의 명시적 요청이 있기 전까지 실행하지 않는다.

## Next.js 작업 규칙

저장소 루트 `AGENTS.md`는 현재 Next.js 버전의 API가 일반적인 Next.js 문서와 다를 수 있다고 명시한다. 새 앱 코드나 설정을 작성하기 전 `node_modules/next/dist/docs/`의 관련 버전 문서를 읽고, 이 저장소의 `src/proxy.ts`처럼 현재 버전의 파일 규칙을 따른다. 예전 `middleware.ts` 규칙을 추측해 적용하지 않는다.
